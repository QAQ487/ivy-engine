# Terrain: heightmap file, local space and triangulation

The engine has no terrain. Ground is an FBX mesh with a `MeshCollider`, which tests every triangle against every nearby body each step (`engine/physics/collider/collider.cpp`), so a large ground mesh is too slow to collide with, and editing it means a round trip through a modelling tool. A terrain system adds a heightmap-based ground that the editor can sculpt. The file format, the coordinate conventions and the triangle split are shared by the renderer, the collider, the editor tools and every saved scene, so they are fixed here before any of them is built.

**Decision**

- **One heightmap per terrain.** Square, `resolution` = 2ⁿ+1 samples per side, from 33 to 4097. Odd sizes give a centre sample and split into equal power-of-two chunks.
- **File:** `rom/terrain/<name>.r16`: `resolution²` little-endian `uint16`, row-major (index = z × resolution + x), no header. This is the raw 16-bit format World Machine, Gaea and Unity export, so heightmaps can be imported unchanged. The resolution is inferred from the file size. Everything else about the terrain (size, height range, layers) lives in the scene JSON of the `Terrain` component, so the file stays a plain grid.
- **Not PNG:** a playable package compresses every `rom/` PNG to BC7 (ADR 0002), which would quantise the heights. `.r16` is never cooked. Splat (paint) maps get their own rule when painting is built.
- **Height** of a sample = `heightOffset + sample / 65535 × heightScale` (metres). `heightScale` 0 to 10000, sizes 1 to 100000; values read from JSON are sanitised (NaN → default, then clamped).
- **Terrain-local space:** sample (0, 0) is the origin; the terrain covers `[0, sizeX] × [0, sizeZ]` on XZ with Y up. The owning GameObject's **position** moves the terrain; its **rotation and scale are ignored** (size comes from `sizeX` / `sizeZ` / `heightScale`). This keeps height queries and the collider a direct grid lookup.
- **Triangulation:** each cell is split along the diagonal from (x, z) to (x+1, z+1), into triangles (a, c, d) and (a, d, b), with a = (x, z), b = (x+1, z), c = (x, z+1), d = (x+1, z+1). Clockwise seen from above (front faces in the engine's left-handed, cull-back setup). Height queries, the collider and the drawn mesh all use this split, so a character stands exactly on the surface that is drawn.
- **Chunks and LOD:** the grid is drawn and culled in square chunks of `chunkQuads` cells (power of two, 8 to 256, default 64; neighbouring chunks share border samples). LOD level L draws every 2ᴸ-th sample and is chosen from the camera's distance to the chunk's bounding box: level L up to `chunkSize × 1.5 × 2ᴸ` (× `lodBias`), with 10% hysteresis when moving to a finer level.
- **Rendering:** the heightmap is uploaded as an R16 texture and the vertex shader reads heights from it, so a sculpt stroke only updates the edited rectangle. A CPU copy stays for collision, culling and height queries. Every chunk draws one shared grid mesh; visible chunks are grouped by LOD level and drawn with one instanced draw per level (instance data: chunk origin and skirt depth). Cracks between chunks at different LOD levels are hidden with skirts that hang from every chunk edge by the chunk's height range. The vertex shader outputs the same data as the regular mesh shader, so terrain is shaded by the scene's default lit pixel shader (one tiled texture until splat painting).
- **Collision:** a dedicated heightfield collider (`ColliderType::TERRAIN`, created by the component, never serialized) tests only the cells under a body: spheres exactly (closest point per triangle; a centre below the surface is pushed out along the surface normal, so fast bodies cannot tunnel), capsules as spheres along the segment, boxes and cylinders by sample points on corners, edges and rims. Raycasts walk the grid. Contacts go through the regular contact solver, with the terrain as a kinematic body. `MeshCollider` is not used for terrain. Scripts read the ground height with `ScriptApi_TerrainSampleHeight` (ScriptRuntimeApi v53).
- **Editing:** sculpt brushes change the CPU map in place and upload only the changed rectangle to the GPU; each stroke is one undo step holding that rectangle before and after. Edited maps are written to their `.r16` when the scene is saved (a terrain without a file gets `rom/terrain/<scene>_<object>.r16`), never on every stroke.
- **Paint layers:** up to 4 layer textures blended by a splat map stored as `.splat` (N×N RGBA8 weights, no header, N = 2ⁿ+1), not PNG, for the same reason as `.r16` (packaging would BC7-compress it). Terrain draws with the regular lit pixel shaders compiled with `TERRAIN_SPLAT`, which only changes how the base colour is sampled, so every lighting feature stays shared. A scene with a single `texture` reads it as layer 0.
- Core logic is `engine/terrain/terrain_heightmap` (pure, Linux-tested by `tests/terrain_heightmap_test.cpp`).

**Considered Options**

- *FBX ground mesh + `MeshCollider`* (status quo): no editor sculpting, and collision cost grows with triangle count.
- *16-bit PNG heightmap*: viewable in image tools, but packaging would BC7-compress it; would need a cook exception and a 16-bit PNG decoder in the runtime.
- *Own file format with a header*: could store size and height range, but would not open in other terrain tools; the scene JSON already carries those values.
- *Applying the GameObject's rotation and scale*: flexible, but every query would need a full inverse transform and non-uniform scale breaks the grid walk; rotated terrain is rare.
- *CPU-built vertex buffers per chunk*: works with the existing shaders, but every sculpt stroke would rebuild buffers and LOD would need one buffer set per level.
- *Multiple terrain tiles / streaming*: deferred; one terrain of up to 4097² samples covers a typical game map.
